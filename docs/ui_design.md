# Streamlit UI 설계

> 현재 Streamlit 앱(`app/streamlit_app.py`), 모델 파일, PostgreSQL 코드 없음. 전부 구현 예정.

---

## 0. 왜 Streamlit인가?

**왜 FastAPI + React/Next.js가 아닌 Streamlit을 쓰는가?**
FastAPI + React 구조는 백엔드 서버와 프론트엔드 앱을 별도로 개발하고 배포해야 한다. 이 프로젝트의 목적은 발로란트 라인업 분석 도구를 로컬에서 빠르게 실험하는 것이다. Streamlit은 Python 스크립트 하나로 UI를 만들 수 있어서 ML 코드와 UI 코드를 같은 파일에서 관리할 수 있다. 클라우드 배포, 외부 API 연동이 없는 로컬 분석 도구 용도에서는 Streamlit이 훨씬 적합하다.

**왜 승률만 보여주지 않고 원인과 변화량도 함께 표시하는가?**
"팀 A 승률 63%"만 나오면 사용자는 어떤 조합을 바꿔야 더 이길 수 있는지 알 수 없다. feature importance와 교체 변화량을 함께 보여줘야 "Controller를 추가하면 승률이 7% 오른다"는 실용적인 판단이 가능해진다. 이것이 이 프로젝트가 다른 단순 승률 예측 도구와 차별화되는 지점이다.

## 1. 공통 레이아웃

```
streamlit_app.py
├── 사이드바 (화면 이동, 모델 선택, DB 연결 상태)
│   ├── 예측
│   ├── 기록
│   └── 분석
└── 메인 영역
    ├── 입력 (선수/요원 조합)
    ├── 예측 결과 (승률, 영향 피처)
    ├── 영향도 설명 (적합도, 시너지/충돌)
    └── 조합 비교
```

| 영역 | 역할 |
|------|------|
| 사이드바 | 화면 이동, 모델 선택, DB 연결 상태 |
| 상단 | 프로젝트명, 현재 모델, 평가 지표 요약 |
| 입력 | 선수/요원 조합, 선수 정보 |
| 결과 | 승률, 주요 영향 피처, confidence |
| 설명 | 선수-요원 적합도, 팀 시너지/충돌 요인 |
| 기록 | PostgreSQL 후보 저장 기록 |

**화면 원칙**: 첫 화면에서 바로 조합 실험 가능. 승률만 표시하지 않고 원인과 변화량 함께 표시.

**Streamlit 컴포넌트 후보**:

| 용도 | 컴포넌트 |
|------|----------|
| 화면 이동 | `st.sidebar.radio` |
| 선수/요원 선택 | `st.multiselect`, `st.selectbox` |
| 수치 입력 | `st.number_input`, `st.data_editor` |
| 모델 실행 | `st.button` |
| 결과 카드 | `st.metric`, `st.columns` |
| 차트 | `st.bar_chart`, Plotly 후보 |

## 3. 예측 화면

선수/요원 조합을 상세 입력받아 모델이 승률과 영향 요인을 출력하는 화면.

### 입력 영역

| 입력 | UI | 검증 |
|------|-----|------|
| Team A/B 선수 | `st.multiselect` | 각 5명 |
| Team A/B 요원 | `st.multiselect` 또는 슬롯별 `st.selectbox` | 각 5명 |
| 선수 정보 | `st.data_editor` | 결측/범위 확인 |

사용자는 피처를 직접 입력하지 않음. Feature Builder가 역할군 카운트, 선수-요원 적합도, 팀 통계를 자동 생성.

**왜 사용자가 피처를 직접 입력하지 않는가?**
모델 입력은 31개 피처(역할군 카운트, diff, agent_map_wr, avg_acs, kd 등)인데, 이 숫자들을 사용자가 직접 계산해서 입력하는 것은 현실적으로 불가능하다. 사용자는 "어떤 선수가 어떤 요원을 들고 어느 맵에서 싸우는가"만 알면 된다. Feature Builder가 그 정보를 받아 31개 피처를 자동으로 계산한다.

### 예측 결과 영역

| 출력 | UI |
|------|-----|
| 팀 A 승리 확률 | `st.metric` 또는 게이지 |
| 팀 B 승리 확률 | `1 - 팀 A 확률` |
| 주요 영향 피처 | bar chart |
| 선수-요원 적합도 | 슬롯별 점수 표 |
| 팀 시너지/충돌 | 텍스트 요약 |

### 교체 실험 영역 (구현 예정)

| 실험 | 예시 |
|------|------|
| 요원 교체 | player1: Jett → Raze |
| 선수 교체 | player1 → candidate1 |
| 역할 조정 | Controller 0명 → 1명 |

출력: 변경 전/후 승률, delta, 기여 피처.

### 저장

예측 실행 후 PostgreSQL 후보 저장소에 입력 조합/모델명/예측 확률/영향 피처/교체 변화량/실행 시각 저장.

## 4. 기록 화면

PostgreSQL에 저장된 과거 조합 실험과 예측 결과를 조회하는 화면.

**왜 예측 기록을 저장하는가?**
같은 조합을 여러 번 실험하거나 "어제 시도한 조합과 오늘 시도한 조합 중 어느 쪽이 더 나은가"를 비교하려면 과거 결과를 다시 불러올 수 있어야 한다. 매번 다시 입력하는 대신 기록에서 불러와 교체 실험을 이어서 할 수 있도록 저장 기능을 제공한다.

| 기능 | 설명 |
|------|------|
| 기록 조회 | 입력 조합, 예측 확률, 모델명, 실행 시각 |
| 필터 | 모델명, 선수명, 요원명, 날짜 범위 |
| 상세 보기 | 영향 피처 + 교체 변화량 |
| 재실행 | 과거 조합을 예측 화면으로 불러오기 |

**테이블 컬럼**: `created_at`, `model_name`, `team_a_players`, `team_a_agents`, `team_b_players`, `team_b_agents`, `win_probability`, `top_factors`

## 5. 분석 화면

모델 성능, 피처 중요도, 조합 실험 결과를 분석가가 검토하는 화면.

**왜 분석 화면이 별도로 필요한가?**
예측 화면은 특정 조합의 승률을 확인하는 데 최적화되어 있다. 분석 화면은 "어떤 피처가 모델 전체에서 가장 중요한가", "RF와 XGBoost 중 어느 모델이 더 정확한가", "어떤 조합이 역사적으로 가장 높은 승률을 기록했는가"처럼 모델 전체 행동을 이해하기 위한 화면이다. 발표나 프로젝트 검증 시 이 화면의 결과를 근거로 사용한다.

**왜 Accuracy만 쓰지 않고 ROC-AUC, F1도 함께 보는가?**
- **Accuracy**: 전체 예측 중 맞춘 비율. 데이터에 승/패가 50:50이면 충분하지만, 실제로 비율이 치우쳐 있으면 항상 한쪽만 예측해도 높게 나올 수 있다.
- **ROC-AUC**: 모델이 "이 경기는 팀 A가 이길 가능성이 더 높다"는 확률적 판단을 얼마나 잘 하는지 측정한다. 0.5는 랜덤과 같고, 1.0은 완벽한 분류다.
- **F1**: 정밀도(맞다고 한 것 중 진짜 맞은 비율)와 재현율(실제 맞는 것 중 맞다고 한 비율)의 조화 평균. 하나만 높고 하나만 낮은 상황을 균형 있게 측정한다.

| 카드 | 내용 |
|------|------|
| 총 예측 횟수 | PostgreSQL 저장 기록 수 |
| 평균 예측 승률 | 기록 기준 평균 |
| 현재 모델 | 선택된 모델명 |
| 평가 지표 | Accuracy, ROC-AUC, F1 |

**차트**: Feature importance, 선수-요원 적합도 Top, 교체 delta Top, RF/XGBoost/LightGBM 비교.

**리포트 출력 후보**: 성능 지표 요약, 주요 피처, 슈퍼팀 후보 조합, 리스크 큰 조합, 교체 추천 근거.
